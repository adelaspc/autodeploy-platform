# PaaS Specification (v1)

## Overview

Defines the structure and requirements of a deployable application.

## Application Specification

```yaml
name: my-app
repo_url: https://github.com/user/project
branch: main
dockerfile_path: Dockerfile
build_context: .
port: 8000
healthcheck_path: /health

env_vars:
  - name: DATABASE_URL
    required: true

migration_command: "flask db upgrade"

cpu: 250m
memory: 512Mi

trigger: manual  # manual | github_push

runtime: dockerfile
```

## User-Supplied Application Spec Fields

- `name`: unique application identifier
- `repo_url`: Git repository containing the application source
- `branch`: branch to deploy from
- `dockerfile_path`: path to the Dockerfile inside the repository
- `build_context`: directory used as Docker build context
- `port`: single exposed HTTP port
- `healthcheck_path`: HTTP endpoint used to verify application health
- `env_vars`: runtime environment variables
- `migration_command`: optional pre-deploy command
- `cpu`: CPU request
- `memory`: memory request
- `trigger`: deployment trigger strategy
- `runtime`: runtime type; v1 supports only `dockerfile`

## Platform-Generated Deployment Metadata

These fields are resolved or generated by the platform during a specific deployment run rather than supplied as part of the base application spec.

- `commit_sha`: exact Git commit being deployed
- `registry`: container registry destination
- `image_name`: name of the produced container image
- `image_tag`: tag of the produced image, usually based on commit SHA or deployment ID
- `image_ref`: fully qualified image reference used by Kubernetes

## Runtime Assumptions

User applications must be:

- stateless
- HTTP services
- Dockerfile-based
- single-process
- single-container
- single-port

## Not Supported for User Applications in v1

- user-managed background worker workloads
- queue consumers
- scheduled jobs
- multi-process applications such as separate web and worker process types
- multiple exposed services from the same app
