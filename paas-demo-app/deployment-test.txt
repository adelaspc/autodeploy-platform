Local MicroK8s Helm Deployment Test

This file captures the exact local Kubernetes deployment test flow that is currently working for this repository.

Prerequisites

- MicroK8s is running.
- The MicroK8s registry addon is enabled and reachable at `localhost:32000`.
- The local registry backing PVC/PV is already fixed and bound.
- Docker can push to `localhost:32000`.
- Helm can reach the local cluster context.

Relevant local chart settings

- values file: `deploy/helm/paas-control-plane/values.local-microk8s.yaml`
- image repository: `localhost:32000/paas-control-plane`
- default image tag in the file: `dev`
- image pull policy: `Always`
- executor mode: `fake`
- workspace hostPath: `/var/tmp/paas-control-plane-workspace`
- shared SQLite DB path inside pods: `/tmp/paas-workspaces/control_plane.db`

1. Verify the local registry is reachable

```bash
curl -fsS http://localhost:32000/v2/_catalog
```

Expected result:

- JSON response, for example `{"repositories":[]}` or a list containing `paas-control-plane`

2. Validate the chart before installing

```bash
helm lint ./deploy/helm/paas-control-plane
helm template ci ./deploy/helm/paas-control-plane -f ./deploy/helm/paas-control-plane/values.ci.yaml > /dev/null
helm template local ./deploy/helm/paas-control-plane -f ./deploy/helm/paas-control-plane/values.local-microk8s.yaml > /dev/null
```

3. Build and push the control-plane image to the MicroK8s registry

```bash
docker build -t localhost:32000/paas-control-plane:dev .
docker push localhost:32000/paas-control-plane:dev
```

If you want a different tag, replace `dev` in both commands and in the Helm command below.

4. Install or upgrade the local Helm release

```bash
helm upgrade --install local ./deploy/helm/paas-control-plane \
  -n paas-local \
  --create-namespace \
  -f ./deploy/helm/paas-control-plane/values.local-microk8s.yaml \
  --set image.tag=dev \
  --wait \
  --timeout 240s
```

Expected result:

- Helm ends with `STATUS: deployed`

5. Verify the release resources

```bash
microk8s kubectl get all -n paas-local
microk8s kubectl get pods -n paas-local -o wide
microk8s kubectl get pods -n paas-local -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .spec.containers[*]}{.image}{" "}{end}{"\n"}{end}'
```

Expected result:

- API pod is `Running` and ready
- Worker pod is `Running` and ready
- Reconciler CronJob exists
- running pods use `localhost:32000/paas-control-plane:dev`

6. Verify the API health endpoint

Start a port-forward:

```bash
microk8s kubectl port-forward -n paas-local service/local-paas-control-plane 18080:5000
```

In another shell:

```bash
curl -fsS http://127.0.0.1:18080/health
```

Expected result:

```json
{"status":"ok"}
```

7. If the install fails, inspect the likely failure points

Migration hook:

```bash
microk8s kubectl get events -n paas-local --sort-by=.lastTimestamp
microk8s kubectl logs -n paas-local job/local-paas-control-plane-migrate --all-containers=true --tail=200
```

API logs:

```bash
microk8s kubectl logs -n paas-local deployment/local-paas-control-plane-api --tail=100
```

Worker logs:

```bash
microk8s kubectl logs -n paas-local deployment/local-paas-control-plane-worker --tail=100
```

Known local assumptions behind this working flow

- The chart creates hook-time `ConfigMap` and `Secret` resources before the migration Job starts.
- The chart uses an init container to fix permissions on the shared hostPath workspace before the main container starts.
- This is a single-node local-development flow. `localhost:32000` is appropriate here, but not for a multi-node cluster.
- This validates the control plane running on Kubernetes with `CONTROL_PLANE_EXECUTOR=fake`. It does not yet validate the user-app Kubernetes executor path.

Validate Helm deployment mode locally

This section validates the user-workload Kubernetes executor path with:

- `CONTROL_PLANE_EXECUTOR=kubernetes`
- `CONTROL_PLANE_K8S_DEPLOYMENT_MODE=helm`
- the `deploy/helm/generic-web-app` chart
- a local sample Node app repository
- a local MicroK8s registry at `localhost:32000`

This is a manual validation flow. It does not change the default executor behavior. The default deployment mode remains `manifest`.

Prerequisites

- MicroK8s is running.
- The MicroK8s registry addon is enabled and reachable at `localhost:32000`.
- Docker can build and push to `localhost:32000`.
- `kubectl` can reach MicroK8s through `CONTROL_PLANE_KUBECONFIG`.
- `helm` is installed and can reach the same cluster through `KUBECONFIG`.
- A `kubectl` executable is available on `PATH`. If you only have `microk8s kubectl`, create the wrapper shown below.
- The control plane Python virtualenv is installed.

1. Verify MicroK8s, registry, kubectl, and Helm

```bash
microk8s status --wait-ready
curl -fsS http://localhost:32000/v2/_catalog
microk8s kubectl get nodes
helm version
microk8s config > /tmp/microk8s-config
KUBECONFIG=/tmp/microk8s-config kubectl get nodes
KUBECONFIG=/tmp/microk8s-config helm list -A
```

Expected result:

- MicroK8s reports ready.
- Registry catalog returns JSON.
- `kubectl get nodes` succeeds.
- `helm list -A` succeeds without needing a live release.

If `kubectl get nodes` fails because `kubectl` is missing, create a local MicroK8s wrapper and keep it on `PATH` in every shell that runs the worker:

```bash
mkdir -p /tmp/paas-bin
cat > /tmp/paas-bin/kubectl <<'EOF'
#!/usr/bin/env bash
exec microk8s kubectl "$@"
EOF
chmod +x /tmp/paas-bin/kubectl
export PATH="/tmp/paas-bin:$PATH"
kubectl get nodes
```

2. Create a sample user app repository

Use a local repository so the development-mode control plane can clone it without GitHub credentials:

```bash
mkdir -p /tmp/paas-helm-mode-node
cd /tmp/paas-helm-mode-node
cat > package.json <<'EOF'
{
  "scripts": {
    "start": "node app.js"
  },
  "dependencies": {}
}
EOF
cat > app.js <<'EOF'
const http = require("http");
const port = process.env.PORT || 3000;

const server = http.createServer((req, res) => {
  if (req.url === "/health") {
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ status: "ok" }));
    return;
  }
  res.writeHead(200, { "content-type": "text/plain" });
  res.end("hello from helm mode\n");
});

server.listen(port, "0.0.0.0");
EOF
cat > Dockerfile <<'EOF'
FROM node:22-alpine
WORKDIR /app
COPY package.json ./
COPY app.js ./
ENV PORT=3000
EXPOSE 3000
CMD ["node", "app.js"]
EOF
git init
git add package.json app.js Dockerfile
git commit -m "Initial sample app"
```

If Git refuses to commit because user identity is not configured, set local test-only values:

```bash
git config user.email "local@example.test"
git config user.name "Local Test"
git commit -m "Initial sample app"
```

3. Build and push the sample image once to verify registry pulls

This step validates the sample app image and registry path independently. The control-plane worker will still build and push its own image during the deployment flow.

```bash
docker build -t localhost:32000/paas-workloads/helm-mode-node:manual .
docker push localhost:32000/paas-workloads/helm-mode-node:manual
curl -fsS http://localhost:32000/v2/_catalog
```

Expected result:

- Docker build succeeds.
- Docker push succeeds.
- Registry catalog includes `paas-workloads/helm-mode-node`.

4. Configure the control plane for local Helm mode

Run these from the `paas-demo-app` directory:

```bash
cd /home/rhaast/autodeploy-platform/paas-demo-app
export CONTROL_PLANE_ENV=development
export CONTROL_PLANE_EXECUTOR=kubernetes
export CONTROL_PLANE_K8S_DEPLOYMENT_MODE=helm
export CONTROL_PLANE_REGISTRY_ENABLED=true
export CONTROL_PLANE_REGISTRY_URL=localhost:32000
export CONTROL_PLANE_REGISTRY_NAMESPACE=paas-workloads
export CONTROL_PLANE_KUBECONFIG=/tmp/microk8s-config
export KUBECONFIG=/tmp/microk8s-config
export CONTROL_PLANE_K8S_NAMESPACE=paas-workloads
export PATH="/tmp/paas-bin:$PATH"
unset CONTROL_PLANE_K8S_IMAGE_PULL_SECRET
```

Important notes:

- `CONTROL_PLANE_KUBECONFIG` is used by the executor's `kubectl` commands.
- `KUBECONFIG` is used by `helm`.
- The worker process must have both `KUBECONFIG` and the `kubectl` wrapper on `PATH`.
- `CONTROL_PLANE_REGISTRY_NAMESPACE` must be set because Kubernetes executor preflight requires registry push configuration.
- Leave `CONTROL_PLANE_K8S_IMAGE_PULL_SECRET` unset for the local unauthenticated MicroK8s registry.

6. Create a user project

Terminal 2:

```bash
PROJECT_RESPONSE=$(
  curl -fsS -X POST http://127.0.0.1:5000/api/projects \
    -H 'Content-Type: application/json' \
    -d '{
      "name": "helm-mode-node",
      "repo_url": "/tmp/paas-helm-mode-node",
      "branch": "master",
      "dockerfile_path": "Dockerfile",
      "build_context": ".",
      "port": 3000,
      "healthcheck_path": "/health",
      "env_vars": [
        {"name": "APP_ENV", "value": "local"}
      ],
      "trigger": "manual",
      "runtime": "dockerfile"
    }'
)
echo "$PROJECT_RESPONSE"
PROJECT_ID=$(python -c 'import json,sys; print(json.load(sys.stdin)["id"])' <<< "$PROJECT_RESPONSE")
echo "PROJECT_ID=$PROJECT_ID"
```

If your local default branch is `main`, change `"branch": "master"` to `"branch": "main"`.

7. Trigger a deployment

```bash
DEPLOY_RESPONSE=$(
  curl -fsS -X POST "http://127.0.0.1:5000/api/projects/${PROJECT_ID}/deploy" \
    -H 'Content-Type: application/json' \
    -d '{}'
)
echo "$DEPLOY_RESPONSE"
DEPLOYMENT_ID=$(python -c 'import json,sys; print(json.load(sys.stdin)["id"])' <<< "$DEPLOY_RESPONSE")
echo "DEPLOYMENT_ID=$DEPLOYMENT_ID"
```

13. Stop the Helm-mode deployment through the control-plane API

Helm mode stop now uses `helm uninstall` through the Kubernetes executor. This validates that the platform removes the Helm release instead of leaving Helm-managed resources orphaned.

```bash
curl -fsS -X PATCH "http://127.0.0.1:5000/api/projects/${PROJECT_ID}/deployments/${DEPLOYMENT_ID}" \
  -H 'Content-Type: application/json' \
  -d '{
    "status": "stopped",
    "message": "Stop Helm-mode deployment"
  }'
```

Expected events include:

- `deployment.stop_started`
- `kubernetes.helm_uninstall_started`
- `kubernetes.helm_uninstall_succeeded`
- `deployment.stopped`

Expected stop metadata includes:

- `deployment_mode: helm`
- `helm_release_name`
- `helm_log_path`
- `helm_returncode: 0`
- `stopped: true`

Verify the Helm release and Kubernetes resources were removed:

```bash
helm list -n paas-workloads
helm status "$RELEASE" -n paas-workloads
microk8s kubectl get all -l app.kubernetes.io/instance="$RELEASE" -n paas-workloads
```

Expected result:

- `helm list` no longer shows the release.
- `helm status` reports the release was not found.
- No Deployment, Service, or Pod remains for `app.kubernetes.io/instance=$RELEASE`.

If the Helm release was already manually removed, stop should still complete successfully and record:

- `kubernetes.helm_uninstall_not_found`
- `deployment.stopped`

14. Manually remove a Helm release if needed

If you need to clean up outside the control-plane API, uninstall the release directly:

```bash
helm uninstall "$RELEASE" -n paas-workloads
```

Then verify:

```bash
helm list -n paas-workloads
microk8s kubectl get all -l app.kubernetes.io/instance="$RELEASE" -n paas-workloads
```

Use direct Helm cleanup only for manual test recovery. The normal Helm-mode stop path should go through the control-plane API.

15. Switch back to manifest mode

Helm mode is not the default. To return to the existing direct manifest path:

```bash
export CONTROL_PLANE_K8S_DEPLOYMENT_MODE=manifest
```

or unset the variable:

```bash
unset CONTROL_PLANE_K8S_DEPLOYMENT_MODE
```

If the API or worker process is already running, restart it after changing the variable.

16. Optional namespace cleanup

After stopping or manually uninstalling the release, you can remove the test namespace:

```bash
microk8s kubectl delete namespace paas-workloads
```

Only delete the namespace if it does not contain resources you want to keep.

Troubleshooting Helm deployment mode

Helm binary missing

- Symptom: worker fails during `kubernetes.helm_deploy_started` / Helm deploy step with a missing executable error.
- Fix: install Helm, export `KUBECONFIG`, and verify from the same shell that will run the worker:

```bash
export KUBECONFIG=/tmp/microk8s-config
helm version
KUBECONFIG=/tmp/microk8s-config helm list -A
```

Helm cannot reach the cluster

- Symptom: `helm_stderr_summary` contains `kubernetes cluster unreachable` and `http://localhost:8080/version`.
- Cause: Helm did not receive the MicroK8s kubeconfig and fell back to the default localhost API URL.
- Fix: export `KUBECONFIG` before running the worker:

```bash
export KUBECONFIG=/tmp/microk8s-config
helm list -n paas-workloads
.venv/bin/python -m flask --app wsgi:app run-worker-once
```

`kubectl` binary missing during healthcheck

- Symptom: worker reaches Helm deploy, then fails during healthcheck with `FileNotFoundError: [Errno 2] No such file or directory: 'kubectl'`.
- Cause: Helm deploy succeeded, but the executor's post-deploy port-forward healthcheck calls a `kubectl` executable.
- Fix: create and export the MicroK8s wrapper before running the worker:

```bash
mkdir -p /tmp/paas-bin
cat > /tmp/paas-bin/kubectl <<'EOF'
#!/usr/bin/env bash
exec microk8s kubectl "$@"
EOF
chmod +x /tmp/paas-bin/kubectl
export PATH="/tmp/paas-bin:$PATH"
kubectl get nodes
.venv/bin/python -m flask --app wsgi:app run-worker-once
```

Chart path not found

- Symptom: Helm stderr mentions that `deploy/helm/generic-web-app` was not found.
- Fix: run the worker from the repository root:

```bash
cd /home/rhaast/autodeploy-platform/paas-demo-app
```

Generated values path issues

- Symptom: Helm stderr mentions a missing values file, or deployment event metadata has an unexpected `values_path`.
- Fix: inspect the deployment workspace under:

```text
${CONTROL_PLANE_WORKSPACE_ROOT:-/tmp/paas-workspaces}/project-<project-id>/deployment-<deployment-id>/logs/
```

Look for:

- `generic-web-app-values.yaml`
- `helm-upgrade-install.log`

Image pull failures from `localhost:32000`

- Symptom: Helm succeeds but Pod remains `ImagePullBackOff` or `ErrImagePull`.
- Fixes:
  - verify the image was pushed:

```bash
curl -fsS http://localhost:32000/v2/_catalog
```

  - verify the Pod image:

```bash
microk8s kubectl get pods -n paas-workloads -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .spec.containers[*]}{.image}{" "}{end}{"\n"}{end}'
```

  - keep this flow on single-node MicroK8s. `localhost:32000` is not appropriate for a multi-node cluster.

Service name or port-forward healthcheck mismatch

- Symptom: Helm release is deployed but worker healthcheck fails during `kubernetes.healthcheck_failed`.
- Check:

```bash
helm status "$RELEASE" -n paas-workloads
microk8s kubectl get svc -n paas-workloads
microk8s kubectl describe svc "${RELEASE}-generic-web-app" -n paas-workloads
microk8s kubectl logs -n paas-workloads -l app.kubernetes.io/instance="$RELEASE" --tail=100
```

- Make sure the project `port` matches the container's listening port.
- Make sure `healthcheck_path` returns HTTP 2xx.

Helm release already exists

- Symptom: rerunning the deployment updates the same release.
- This is expected. Helm mode uses one release per project/environment so redeploys use `helm upgrade --install`.
- To force a clean release:

```bash
helm uninstall "$RELEASE" -n paas-workloads
```

Invalid `CONTROL_PLANE_K8S_DEPLOYMENT_MODE` value

- Symptom: executor creation fails with a message that the mode must be `manifest` or `helm`.
- Fix:

```bash
export CONTROL_PLANE_K8S_DEPLOYMENT_MODE=helm
```

or:

```bash
export CONTROL_PLANE_K8S_DEPLOYMENT_MODE=manifest
```
