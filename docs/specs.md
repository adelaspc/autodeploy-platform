# PaaS Specification (v1)

## Overview

Defines the structure and requirements of a deployable application.

## Application Specification

```yaml
name: my-app
repo_url: https://github.com/user/project.git
branch: main
dockerfile_path: Dockerfile
build_context: .
port: 8000
healthcheck_path: /health

env_vars:
  - name: DATABASE_URL
    required: true
  - name: APP_ENV
    value_source: configmap_key_ref
    source_name: my-app-config
    source_key: app-env

migration_command: "flask db upgrade"

cpu: 250m
memory: 512Mi

trigger: manual  # manual | github_push

runtime: dockerfile
```

## User-Supplied Application Spec Fields

- `name`: unique application identifier
- `repo_url`: GitHub HTTPS repository URL containing the application source; accepted without or with `.git`, stored canonically with `.git`
- `branch`: branch to deploy from
- `dockerfile_path`: path to the Dockerfile inside the repository
- `build_context`: directory used as Docker build context
- `port`: single exposed HTTP port
- `healthcheck_path`: HTTP endpoint used to verify application health
- `env_vars`: runtime environment variables; in Kubernetes mode, referenced entries use `value_source` of `configmap_key_ref` or `secret_key_ref` plus `source_name` and `source_key`
- `default_test_command`: optional argv-style test command inherited by new deployments
- `migration_command`: optional argv-style command validated and stored for compatibility; it is reserved by the spec and is not executed or revalidated by the worker
- `cpu`: CPU request
- `memory`: memory request
- `trigger`: deployment trigger strategy
- `runtime`: runtime type; v1 supports only `dockerfile`

Command fields are not shell scripts. The API accepts simple commands such as `pytest -q`, `python -m pytest`, `python -m py_compile server.py`, `npm test`, and `ruff check .`. Shell wrappers and control operators such as `sh -c`, `bash -c`, `&&`, `||`, `|`, redirection, backticks, and subshells are rejected.

## Kubernetes Env Var Rules

When the active executor is Kubernetes, project validation applies additional schema checks to `env_vars`:

- each `name` must be a valid Kubernetes environment variable name
- each referenced `source_name` must be a valid Kubernetes resource name
- each referenced `source_key` must be non-empty
- duplicate env var names are rejected

These are API-layer schema checks only. Existence of the referenced `ConfigMap` and `Secret` resources is still validated later during deploy-time Kubernetes preflight.

## Platform-Generated Deployment Metadata

These fields are resolved or generated by the platform during a specific deployment run rather than supplied as part of the base application spec.

- `commit_sha`: exact Git commit being deployed
- `registry`: container registry destination
- `image_name`: name of the produced container image
- `image_tag`: tag of the produced image, usually based on commit SHA or deployment ID
- `image_ref`: fully qualified image reference used by Kubernetes

The worker verifies `image_ref` remotely after push and before deployment. This verification is distinct from the persisted registry push result.

## Runtime Assumptions

User applications must be:

- stateless
- HTTP services
- Dockerfile-based
- single-process
- single-container
- single-port

## Not Supported for User Applications in v1

- user-managed background worker workloads
- queue consumers
- scheduled jobs
- multi-process applications such as separate web and worker process types
- multiple exposed services from the same app
