# PaaS Specification (v1)

## Overview

Defines the structure and requirements of a deployable application.

## Application Specification

```yaml
name: my-app
repo_url: https://github.com/user/project.git
branch: main
git_auth_type: token  # none | token
git_secret_ref: GITHUB_TOKEN  # required when git_auth_type is token
dockerfile_path: Dockerfile
build_context: .
port: 8000
healthcheck_path: /health

env_vars:
  - name: DATABASE_URL
    value_source: secret_key_ref
    source_name: my-app-secret
    source_key: database-url
  - name: APP_ENV
    value_source: configmap_key_ref
    source_name: my-app-config
    source_key: app-env

migration_command: "flask db upgrade"

cpu: 250m
memory: 512Mi

trigger: manual  # manual | github_push

runtime: dockerfile
```

Each `env_vars` entry is required by virtue of being present in the project
specification; `required` is not an API field. Literal values use
`value_source: literal` and `value`, while sensitive values should use
`value_source: secret_key_ref` with `source_name` and `source_key`. The API
validates the reference shape; the referenced Kubernetes Secret or ConfigMap
must exist when the workload is deployed.

## User-Supplied Application Spec Fields

- `name`: unique application identifier
- `repo_url`: GitHub HTTPS repository URL containing the application source; accepted without or with `.git`, stored canonically with `.git`
- `branch`: branch to deploy from
- `git_auth_type`: `none` for public repositories or `token` for GitHub HTTPS token authentication
- `git_secret_ref`: symbolic environment-variable name holding the GitHub token when `git_auth_type` is `token`; the token value is never stored in the project
- `dockerfile_path`: path to the Dockerfile inside the repository
- `build_context`: directory used as Docker build context
- `port`: single exposed HTTP port
- `healthcheck_path`: HTTP endpoint used by the worker's rollout check and by Kubernetes readiness and liveness probes in both Kubernetes deployment modes
- `env_vars`: runtime environment variables; referenced entries use `value_source` of `configmap_key_ref` or `secret_key_ref` plus `source_name` and `source_key`
- `default_test_command`: optional argv-style test command inherited by new deployments
- `migration_command`: optional argv-style command validated and stored for compatibility; it is reserved by the spec and is not executed or revalidated by the worker
- `cpu`: optional positive Kubernetes CPU request (`250m`, `0.5`, or `1`), applied in both manifest and Helm modes; precision finer than `1m` is rejected
- `memory`: optional positive whole-byte Kubernetes memory request (`512Mi`, `1Gi`, or `100M`), applied in both manifest and Helm modes
- `trigger`: deployment trigger strategy
- `runtime`: runtime type; v1 supports only `dockerfile`

Command fields are not shell scripts. The API accepts simple commands such as `pytest -q`, `python -m pytest`, `python -m py_compile server.py`, `npm test`, and `ruff check .`. Shell wrappers and control operators such as `sh -c`, `bash -c`, `&&`, `||`, `|`, redirection, backticks, and subshells are rejected.

## Kubernetes Env Var Rules

Project validation applies Kubernetes reference checks whenever an entry uses `configmap_key_ref` or `secret_key_ref`, even if another executor is active. This prevents an invalid reference from being persisted and failing only after a later executor change:

- each referenced `source_name` must be a valid DNS-subdomain Kubernetes resource name of at most 253 characters
- each referenced `source_key` must contain 1–253 letters, digits, `-`, `_`, or `.`; `.`, `..`, path separators, whitespace, and `..`-prefixed keys are rejected
- when the active executor is Kubernetes, each `name` must be a valid Kubernetes environment variable name and duplicate env var names are rejected
- project payloads accept at most 100 environment entries; literal values must be strings and are length-bounded

These are API-layer schema checks only. Existence of the referenced `ConfigMap` and `Secret` resources is still validated later during deploy-time Kubernetes preflight.

## Platform-Generated Deployment Metadata

These fields are resolved or generated by the platform during a specific deployment run rather than supplied as part of the base application spec.

- `commit_sha`: exact Git commit being deployed
- `registry`: container registry destination
- `image_name`: name of the produced container image
- `image_tag`: local image name and commit-prefixed unique tag generated for each build
- `image_ref`: fully qualified image reference; registry-backed runs persist `repository@sha256:...` after push

The platform also injects two reserved workload environment variables immediately before deployment. `APP_COMMIT_SHA` is the exact build commit SHA and `APP_VERSION` is the unique build image tag. These names are not part of the project-controlled configuration: values configured under either name are replaced in fake, local Docker, Kubernetes manifest, and Kubernetes Helm execution.

The worker captures the digest reported by push and verifies that exact `image_ref` remotely before deployment. Registry-disabled local runs keep a local tag reference. This verification is distinct from the persisted registry push result.

## Runtime Assumptions

User applications must be:

- stateless
- HTTP services
- Dockerfile-based
- single-process
- single-container
- single-port

## Not Supported for User Applications in v1

- user-managed background worker workloads
- queue consumers
- scheduled jobs
- multi-process applications such as separate web and worker process types
- multiple exposed services from the same app
